# AGENTS.md

Guidance for coding agents working in this repository.

## Repository model

cssnano is a modular CSS minifier built on PostCSS, in a pnpm workspace:

- `packages/cssnano` is the main package. It contains the presets, every
  optimization plugin and the shared CSS utilities:
  - `src/presets/{default,lite,advanced}.js` provide conservative semantic
    optimizations (`default`), assumption-making transforms (`advanced`), and
    comment, whitespace, and empty-node cleanup only (`lite`).
  - `src/plugins/<postcss-plugin-name>/` holds each plugin. Its tests, perf
    files, scripts and mutation catalogs mirror that name under `test/`,
    `perf/`, `script/` and `mutation/`, and its documentation is
    `docs/<postcss-plugin-name>/README.md`.
  - `src/pipeline/` holds the host plugin (`host.js`) that runs a preset's
    plugins as stages in one walk of the stylesheet, and the walkers it drives
    (`walkDown.js`, `walkUp.js`). Tests mirror it under `test/pipeline/`.
  - `src/values/` holds `ValueBuffer`, the token list that stages read and
    edit, and the token constructors and microsyntax helpers beside it.
    Tests mirror it under `test/values/`.
  - `src/passes/merge/` holds the transforms that run inside the one
    `cssnano-merge` plugin: longhand merging (`lib/longhand/`), rule merging
    (`lib/rules/`) and duplicate discarding (`lib/duplicates/`); `index.js`
    drives them. `src/passes/ir/` holds the records they run on;
    `src/passes/ir/data/properties.json` is regenerated by `acquire:passes-ir`. Tests, perf
    files, scripts and mutation catalogs mirror these paths under
    `test/passes/`, `perf/passes/`, `script/passes/` and `mutation/passes/`.
  - `src/utils/` holds the shared CSS parsing and manipulation utilities.
    `src/utils/stylehacks/` holds the browser-hack detectors that the longhand
    merge uses; it is not a PostCSS plugin.
  - Code imports neighbouring modules by relative path. Add a private `#`
    specifier to `package.json` `imports` only for a subsystem entry point
    reached from many distant directories (such as `#utils`, `#stylehacks`,
    `#passes/merge`, `#postcss-*`), or for a module that tests, scripts or
    `util/` would otherwise reach through `../../src/` paths.
- `packages/postcss-svgo` is a separate published package with its own helper
  copies.
- `util` holds shared test, integration, fuzzing, mutation, build and
  benchmark support; benchmarking lives under `util/benchmark/`.
- `site` holds the Astro documentation site.

In each package, source is in `src`, generated declarations in `types`, and
tests in `test`.

## Goals and evaluation

Every change should make the intended CSS transformation clearer while preserving CSS semantics and the repository’s supported compatibility behavior.

- Test a plugin change with focused unit tests and, when composition or output size can change, with preset integration tests.
- Treat tests as executable contracts. Test names should identify the subject and the behavior being asserted, not merely the test framework.
- Follow a test-first workflow for behavior changes and bug fixes: add or update the focused test that expresses the intended contract before changing production code, run it to establish the expected failure when practical, then implement the change and rerun the test. If the behavior cannot be specified independently of the implementation, explain that exception and add the test as soon as the contract is clear.
- Keep independently meaningful contracts in separate tests, with one behavioral assertion per test where practical.
- Avoid echo tests (tautological verification): when testing data sets, tables, or constants, assert independent domain invariants (such as set equivalence against an authoritative specification, structural syntax constraints, disjointness, and immutability) or consumer transform behavior. Do not merely assert reference identity of internal exports or spot-check a subset of the implementation's hardcoded literals.
- Preserve existing coverage and investigate fixture changes rather than dismissing them as generated noise. Inputs may include invalid CSS, and their output can still be intentional.
- A transform must never turn an invalid declaration into a valid one, or drop a component it does not understand. Browsers ignore invalid declarations, so making one valid changes how the page renders. When unsure, leave the value byte-identical.
- Before collapsing a multi-value form to a shorter one, check what the grammar fills in for each omitted part (positions, margin/padding shorthands, `border-radius`, and so on). For example, a single `<position>` value implies `center` on the other axis, and a single number is always horizontal.
- A test that expects unchanged output must say in its name or a comment why the value cannot be shortened.
- A change should preserve or improve performance and asymptotic complexity. Avoid quadratic time in tests, scripts and algorithms; look for linear time. Performance refactors must preserve byte output unless an intentional output change is documented. Compare matched production benchmarks and measure independent hypotheses separately.
- A refactor must not add parses, closures, callback arguments, temporary arrays or objects, or new key strings on any path the replaced code did not take. A wrapper must forward to the same underlying operation. Pin the contract with a test where it is observable.
- Prefer the simplest code to a cache. Do not add a memo for what it might save: add one only where a count shows the work it saves, and pin it with a scaling test under `perf/`. A refactor may remove a memo that no scaling test pins and recompute what it saved, in place of the rule above, provided its commit message names the memo and the work it adds back. Interning, which gives equal values one id so they compare as integers, is not a memo.

## Running checks

- `pnpm test` is the one test command. With no arguments it runs every check
  that gates a change: types, lint, format, every test, the site's tests, the
  framework fixtures and the mutation baselines. A step that cannot run here
  (the site's tests without `site/node_modules`, the mutation baselines below
  Node 24) is skipped, not passed. With paths
  (`pnpm test packages/cssnano/test/passes/merge/`, which recurses) it runs
  only those tests, for iterating.
- The cheap steps (types, lint, format, the stale-mutation check) run first and
  together. If one fails, the slow steps (tests, site, frameworks, mutation
  baselines) do not start, and the last line lists them as `notrun=`; `skipped=`
  still means a step that cannot run here. `pnpm test --keep-going` runs the slow
  steps anyway.
- Before handoff, run `pnpm test` with no arguments and quote its last line,
  `test: done status=pass|fail failed=… skipped=… notrun=…`. Report every
  skipped, not-run or failed step, and do not claim full verification while
  one remains. A failed step's full output is in `test-results/<step>.log`.
- The types step regenerates the declarations in `types/`; commit their diff
  with the change. For other generated data, regenerate first, then run
  `pnpm test`; do not rely on inspection alone.
- When production output changes intentionally, run `pnpm build:integration`
  to update the framework fixtures, then review the diff; `pnpm test` fails
  while they are out of step. `pnpm fixlint` applies the formatter and lint
  fixes.
- Run `pnpm test`, benchmarks and mutation testing with `run_in_background`,
  do not poll or sleep, and wait for the exit notification. Each ends with
  `test: done`, `bench: done` or `mutation: done`, then `status=pass|fail ...`.
  To see where a run is, read its step or progress lines. A run without a
  `done` line crashed or was killed, and its partial output is not a result;
  if it may still be going, check `pgrep -f` for it before discarding it.
  Never judge a run from filtered output: a pipe into `grep` or `tail`
  replaces its exit code.
- Benchmark with `pnpm run bench:check --case=<name>`, `--set=<name>` or
  `--package=<name>` only, picking the narrowest case. Use `bench:compare`
  (`bench:check --corpus`) only when the user asks for it. A benchmark always
  runs its minimum blocks and `--budget` does not shorten that, so never raise
  or wrap a timeout to compensate. `util/benchmark/README.md` has the options
  and the verdict rule.
- Uncovered branches: `node util/uncoveredBranches.js <dir>`, where `<dir>` is
  `packages/cssnano`, a plugin such as
  `packages/cssnano/src/plugins/postcss-colormin`, or
  `packages/cssnano/src/utils/stylehacks`. It runs those tests under coverage
  and prints every 0-hit branch with its line and source; later arguments go
  to `node --test`, and `--save-lcov=<path>` keeps the lcov report.

## Shared checkout

- One agent session works in a checkout. A second session works in its own
  `git worktree`, so neither changes files under the other's runs.
- Never use `git stash` to reach another revision: it swaps the files under
  any run in the checkout. To run at another revision with a dirty tree, use
  `git worktree add ../<repo>-<name> <rev>` and run
  `pnpm install --frozen-lockfile` in it.
- Keep results and other scratch files outside the checkout: `pnpm test`
  format-checks untracked files too.
- `plans/` is untracked. Tracked code, comments and documentation must not
  cite its steps or items.

## Mutation testing

Mutation testing (Node 24 or later) judges whether the tests or the fuzz
oracles notice a curated fault. Run it only through the runner, never a
hand-copied module or a string replacement, which silently tests the
unmutated code.

- Mutants read the live source tree. Do not edit files while a mutation run is
  going, and run one mutation command at a time, each with its own `--out`
  (the runner refuses an existing file). Overlapping runs cause false timeouts
  and invalid comparisons.
- For a group of catalogs, run `pnpm mutation --group <name>`. Groups are in
  `packages/cssnano/mutation/catalogs.js` (`merge` is the merge gate), which
  is also where a new catalog is registered. A group picks each catalog's
  check and whether unkilled mutants fail it. Every mutation is first applied
  in memory: one whose fragment no longer matches is `stale` and fails the run
  before any mutant runs, so update or delete it in its catalog.
- To compare with the parent, run at the parent with `--out ../parent.json`
  before the change's first edit, while the tree is still clean (or in a
  worktree at the parent), then at the change with
  `--baseline ../parent.json`. A mutant the parent killed and the change did
  not fails the run.
- `pnpm mutation --all` reruns each catalog's test file; add
  `--check oracle --allow-unkilled` for the fuzz suites. Probe one mutant with
  `node util/mutation-testing/mutation-runner.js --catalog <file> --only '<regex>'`
  for its test file, or add
  `--check oracle --suites <module> --allow-unkilled` for the fuzz suites.
- Read the `Running N mutants` line, the last line, which has every count and
  the results file, and the `not killed` lines above it. Only `killed` is a
  verdict in favor of the tests. `survived`, `unchanged` and `not reached`
  mean the mutant was not caught; `errored` and `timed out` mean it was not
  judged. A catalog whose baseline failed is `errored` with the cause in its
  detail: fix that harness problem before comparing against a parent. A run
  with no mutants, an `--only` pattern that matches none, or a test file that
  runs no tests fails.

## Durable conventions

- Use Node’s built-in `test` module for repository package tests and the shared helpers. Plugin and preset tests use `processCSSFactory()` from `util/testHelpers.js`, and preset tests that need a processor call `postcss()` directly.
- Tests that assert wall-clock time or asymptotic scaling, and fuzz or exhaustive sweeps that take about a second or more, go in `packages/<pkg>/perf/` (plain `.js`, not `*.test.js`), so `pnpm test` and the coverage run skip them. Run one with `node --test <file>`; CI runs them without gating. Keep correctness assertions in `test/`.
- Follow the existing test filename convention for the package or subsystem (`*.js` and `*.test.js` are both present). Use `describe()` when it improves source readability without disturbing unrelated test order, and keep nesting shallow: no suites that only wrap a package or preset.
- Apply the rule of three before extracting test helpers: tolerate small duplication until a third consumer needs the same setup or assertion contract.
- Keep generated integration fixtures synchronized with their sources. Do not hand-edit generated site data.
- Use pnpm for dependency and lockfile changes; never edit lockfiles by hand. To repair missing dependencies or workspace links, run `pnpm install --frozen-lockfile`; an install that changes the lockfile needs the user's approval. Never manually create, remove, move, or retarget files or symlinks under `node_modules`.
- Every dependency on a package of this workspace uses the `workspace:^` protocol in package manifests, never a registry semver range. Search all package manifests when changing one.
- When transforming CSS token microsyntaxes (such as `<an-plus-b>` formulas, attribute modifiers, and namespace qualifiers), never use regex or broad string replacements. Always respect token-boundary microsyntax specifications (CSS Syntax 3 and Selectors 4).
- Keep runtime behavior unchanged during types-only cleanup.
- Write code comments so they state the goal or the leading idea; do not add lines of implementation details. Comments explain why, stay under 60 words when practical, and match the behavior. Use vocabulary that a CSS expert, designer or programmer would use; do not invent an idiosyncratic project-specific language.
- Documentation describes stable public contracts and security boundaries, not incidental implementation details. Its current-state claims match the checked-out branch; describe unmerged or branch-specific architecture as such.
- Use precise W3C and MDN terminology and standard algorithm textbook terminology when naming functions and variables.
- Follow the repository’s lint rules, including the configured complexity and syntax restrictions, and use Conventional Commits.
- Distinguish integers from floating-point numbers in both JavaScript runtime arithmetic and CSS domain semantics:
  - In JavaScript, numbers are IEEE-754 double-precision floats. Keep integer math (such as hashes, indices, and offsets) strictly within `Number.MAX_SAFE_INTEGER` ($2^{53} - 1$), avoid accidental float division/modulo precision loss, and respect the repository's `no-bitwise` lint rule without producing fractional values.
  - In CSS transforms, never conflate CSS `<integer>` (e.g. `z-index`, `order`, grid tracks, `An+B` formulas) with CSS `<number>` (e.g. `opacity`, `flex-grow`, `line-height`). Transformations must preserve integer syntax where the specification requires it.
- Do not add changesets for internal refactors that do not change the public package behavior or API.

## Site boundary

Astro is the site’s generator and build path. Site changes must preserve base-aware routing, public assets, generated data, and sitemap behavior. Keep site-specific installation and validation details in `CONTRIBUTING.md` and `site/README.md` rather than duplicating them here. The site publishes `CONTRIBUTING.md`, `CONTRIBUTORS.md` and the `cssnano` changelog as pages, so links in them must be absolute.
